# 非开发工作场景与交付要求填报说明

## 1. 填报目的与范围

请梳理研发人员承担的非开发工作场景，并填写每种场景的工作内容、交付内容、交付方式、交付要求和评估标准（基线工时）。收集结果用于统一确认交付标准及工作量评估标准。

本次每行填写一种可复用的工作场景。无需逐条登记历史任务，也无需提交具体任务的描述文档、附件或实际工时。填报人需提出该场景的基线工时及适用条件，供汇总后统一确认；暂时无法确定的数值标注“待确认”。

这里的非开发工作，是以分析结论、数据处理结果、系统操作结果或支持服务结果为主要交付的工作。执行中使用 SQL、命令或脚本，不影响它作为非开发场景被收集。若主要交付是新增或修改软件功能，则归入开发工作；一项实际任务同时涉及两类工作时，本表只描述其中可区分的非开发部分。

任务描述文档可以直接承载部分场景的交付结果。另一些场景需要通过文件、日志、报表等附件交付。填报人需要说明适合该场景的方式，以及具体应写什么、附什么。

## 2. 填报对象与填写粒度

填报人可从本人或团队熟悉的日常工作中归纳场景，例如统计分析、数据核对、数据迁移、数据修正、配置调整、部署发布、故障排查和技术答疑。上述类别用于启发收集，可按实际工作补充。

场景名称使用“工作对象＋工作动作”表达，例如“业务数据统计分析”“历史数据迁移”“生产故障原因排查”。名称应让其他团队能够判断自己的工作是否属于这一场景。

| 填写粒度 | 示例 | 处理方式 |
| --- | --- | --- |
| 过于宽泛 | 系统维护、日常支持、其他工作 | 按主要工作和交付结果细分 |
| 适合收集 | 应用配置调整及验证、业务数据差异核对 | 每种场景填写一行 |
| 具体项目任务 | 某项目本周仓库历史数据迁移 | 提炼为“历史数据迁移”，保留该类工作的共性 |
| 过于细碎 | 登录服务器、执行一条查询、下载日志 | 作为所属场景的操作步骤填写 |

工作内容和交付要求相同、仅项目名称不同的场景可以合并。若交付内容或完成标准明显不同，应分行填写。例如“问题原因排查”交付定位结论，“故障恢复处理”交付处理操作和恢复结果，两者可以分别收集。

单个场景内部有条件差异时，可以在同一行写清条件。例如简单核对可直接记录结果，逐条差异核对则需要结果清单；不必为每种文件格式新增一个场景。

## 3. 收集表字段

请按下表七个字段填写。无法明确的内容标注“待确认”，并说明待确认的问题；不适用的内容填写“无”并简述原因。

| 字段 | 填写要求 | 示例 |
| --- | --- | --- |
| 工作类别 | 填所属大类，便于汇总相近场景 | 数据处理 |
| 工作场景 | 填可独立识别的具体工作类型 | 历史数据迁移 |
| 工作内容及边界 | 写通常包含的活动，以及容易与其他工作重复的边界 | 使用已有工具迁移指定范围的数据并核对；不含迁移工具功能开发 |
| 交付内容 | 写完成后应留下的过程、结论或结果 | 迁移操作记录、执行结果、源目标数据核对结论 |
| 交付方式 | 从三种方式中选择；有条件差异时说明适用条件 | 两者结合 |
| 交付要求 | 写明任务描述中应记录哪些内容、附件应包含什么、怎样判断交付完整 | 描述中写范围及完成结论；附件提供执行命令、相关日志和核对结果 |
| 评估标准（基线工时） | 写明计量单位、基线工时、适用条件和取值依据；有分档时分别说明 | 每个迁移批次：__人时；注明源目标范围、转换及核对要求，并说明工时依据 |

### 3.1 工作类别与工作场景

工作类别用于归组，工作场景用于识别具体工作。同一类别可以包含多个场景，例如“数据处理”下可以填写数据迁移、数据修正和数据核对。

不要只写技术名称，例如“Oracle”“Linux”“Excel”。应说明使用这些技术完成什么工作。技术差异会改变交付要求时，再把相应条件写入工作内容或交付要求。

### 3.2 工作内容及边界

填写该场景通常处理的对象、主要活动及结束位置。可以按“包含：……；不包含：……”组织文字。

例如，数据差异核对可以包含确定核对口径、执行查询、比较差异和形成结论。数据修正若作为独立场景，应注明不在核对场景内重复计算。某个步骤只在特定情况下发生时，使用“涉及……时，包含……”说明，不把所有可能活动都列为固定要求。

### 3.3 交付内容

交付内容回答完成后留下什么。例如分析结论、核对清单、操作记录、配置变更记录或恢复验证结果。工作动作“执行查询”对应的交付可以是查询口径、结果及结论。

避免只写“完成工作”“提供材料”“提交报告”。应写明报告或记录包含的业务内容。对于操作类场景，应区分准备使用的命令与实际执行结果：若交付目标是操作完成，仅提供命令通常不足以表达完成情况。

### 3.4 交付方式

“交付方式”统一使用第 4 节的三个选项。每行说明该场景的交付信息放在哪里。

已有任务描述文档的基本要求不在本次重新收集。“任务描述中写明即可”表示完成结果可以直接写入该文档；“需要额外附件”表示主要产物需要以附件形式保留；“两者结合”表示描述中的说明和附件中的材料共同构成交付。

### 3.5 交付要求

交付要求要能指导执行人准备材料，也能让查看人判断内容是否齐全。建议采用下面的写法，按场景保留适用部分：

```text
任务描述中记录：……
额外附件提供：……
交付完整的判断：……
条件要求：涉及……时补充……；不涉及则无需提供。
```

应区分固定要求与条件要求。例如“发生异常时附异常处理记录”不能写成所有任务必须提交异常处理记录。附件列出可替代形式时，注明“任选一种”或“按实际使用工具提供”，避免被理解为所有格式都要提交。

### 3.6 评估标准（基线工时）

填写在明确条件下，完成一个工作单位并满足交付要求所需的正常人工投入。统一使用“人时”，多人参与时按投入合计；使用“人日”时注明一天折合多少小时。

建议在同一单元格内按下面的格式填写：

```text
计量单位：每次／每个批次／每套明确口径的分析等。
基线工时：__人时／单位。
适用条件：该工时覆盖的工作范围、规模和操作条件。
取值依据：已有标准、同类工作经验或团队讨论建议，并注明是否待确认。
分档或额外工作：有明确差异时分别写条件和工时；无则填写“无”。
```

基线工时覆盖本行“工作内容及边界”内的活动和相应交付材料准备。避免只填“2小时”却不说明对应一次什么工作，也不要仅用“简单／复杂”区分档位。确需分档时，应写清可识别的条件，例如单一数据源既定口径查询与跨系统口径核对。

优先依据已有标准或同类工作经验提出工时。仅为个人建议时注明“建议值，待确认”；缺乏依据时填写“基线工时待确认”，先写清计量单位和适用条件。不要为了填满表格编造数值。

自动运行、系统等待和人工操作应区分。基线工时只计人工投入，需要持续值守时说明值守如何计入。同一项准备或核对工作不得在多个场景中重复计入；附件数量、命令条数和文档篇幅不直接作为计价单位。

## 4. 交付方式的选择

选择能完整表达该场景交付结果的方式。短文本能够说明清楚的内容，可以直接写在任务描述中；需要保留结构化数据、可执行文件或详细过程记录时，说明附件要求。

| 交付方式 | 适用情况 | 任务描述中的交付内容 | 附件要求 |
| --- | --- | --- | --- |
| 任务描述中写明即可 | 工作结果可以通过简短文字、表格或少量命令完整说明 | 直接写清处理事项、关键过程、结论或验证结果 | 无需额外附件 |
| 需要额外附件 | 主要产物是需要单独使用或查看的文件，如结果数据集、完整报表 | 标明产物名称及对应附件即可；无需抄写文件内容 | 提供完整产物及必要的使用说明 |
| 两者结合 | 需要文字交代范围与结论，同时需要附件承载详细过程或结果 | 写明范围、处理概要、结果结论和附件对应关系 | 提供支撑过程或结果的材料 |

附件可以是任务附件，也可以是团队认可、查看人可访问的文件链接。产出包是与该项工作对应的一组交付材料，可以由任务描述和若干附件共同组成，无需统一压缩成 ZIP，也不要求统一文件格式。

填写附件要求时，只列该场景需要的材料。截图、日志、SQL、脚本和报表各有用途，不应给每个场景套用同一套清单。涉及账号、个人信息或业务敏感数据时，说明采用脱敏内容或受控访问方式；不要要求交付明文密码、密钥或令牌。

## 5. 填报步骤

按下面顺序整理场景，可以先写自己熟悉的部分，再补充待确认内容。

1. 列出团队常见的非开发工作，使用可复用的场景名称。
2. 合并仅项目名称不同的场景，拆分交付目标明显不同的场景。
3. 写清工作内容及边界，标明条件性活动。
4. 列出完成后应留下的交付内容。
5. 选择交付方式，分别写清描述内容和附件要求。
6. 填写评估标准（基线工时），注明计量单位、适用条件和取值依据，检查是否存在重复计量或无法执行的交付要求。

填报人可提出当前实际能够形成的产物，也可以提出建议补充的产物。对尚未形成团队共识的要求，标注“建议要求，待确认”，不要当作已经执行的统一制度。

## 6. 场景填写示例

以下示例用于说明填写方法，属于建议写法。填报人应根据团队工作调整范围和交付要求。基线工时用“__”留待填报人依据经验或已有标准填写，无法确定时写“待确认”；示例不预设工时数值，也不表示这些场景已经纳入系统评估。

### 6.1 技术使用咨询答疑

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 技术支持 |
| 工作场景 | 现有系统使用与技术咨询答疑 |
| 工作内容及边界 | 了解问题、查阅现有资料、给出适用建议或操作说明；不含新增功能开发，不含需要实际修复系统的故障处理 |
| 交付内容 | 问题说明、答复结论、适用条件和后续处理建议 |
| 交付方式 | 任务描述中写明即可 |
| 交付要求 | 在任务描述中写清咨询问题、采用的结论及依据；有操作步骤时直接列出；问题未解决时写清当前结论和待处理事项；无需为简短答复另写一份报告 |
| 评估标准（基线工时） | __人时／个独立咨询问题；适用条件：基于现有资料完成答复，不含复现实验和跨领域专项调查；取值依据：待填；超出条件时另列适用档位及工时 |

### 6.2 简单应用配置调整

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 系统维护 |
| 工作场景 | 现有应用少量配置项调整及验证 |
| 工作内容及边界 | 确认配置项、调整配置、使配置生效并验证；不含应用功能开发和批量环境改造 |
| 交付内容 | 配置变更记录、生效操作和验证结果 |
| 交付方式 | 任务描述中写明即可 |
| 交付要求 | 写明目标环境、配置项、变更前后内容或脱敏摘要、执行操作和验证结果；少量命令可直接记录在描述中；涉及大量配置差异或需保留完整日志时，补充附件并采用“两者结合” |
| 评估标准（基线工时） | __人时／次配置调整；适用条件：单一应用、单一环境，配置项范围明确，包含生效操作及约定验证；取值依据：待填；批量环境调整另列标准 |

### 6.3 业务数据统计分析

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 数据分析 |
| 工作场景 | 业务数据统计分析及结论输出 |
| 工作内容及边界 | 明确统计口径、查询或处理数据、分析结果并形成结论；不含报表功能开发，不含业务数据修正 |
| 交付内容 | 分析口径、分析过程、结果表或图表、分析结论 |
| 交付方式 | 两者结合 |
| 交付要求 | 描述中写明分析目标、数据范围、关键口径及结论；附件提供实际使用的查询 SQL、分析脚本或操作步骤说明，以及结果表或图表；按实际分析方式提供过程材料，无需同时具备 SQL 和脚本 |
| 评估标准（基线工时） | __人时／套分析；适用条件：需填明数据源、指标和分析维度范围，包含过程材料、结果及结论整理；取值依据：待填；跨系统关联或专项清洗可按明确条件分档 |

### 6.4 按既定口径导出数据

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 数据服务 |
| 工作场景 | 按既定筛选条件导出结果数据集 |
| 工作内容及边界 | 按明确口径查询、导出并检查文件；不含探索性分析和业务结论研判 |
| 交付内容 | 可使用的结果数据文件 |
| 交付方式 | 需要额外附件 |
| 交付要求 | 提供结果文件；文件或随附说明中写明筛选范围、字段含义及数据对应时间；描述中标明附件即可；结果为空时说明无匹配数据；不额外要求制作分析报告 |
| 评估标准（基线工时） | __人时／次数据导出；适用条件：筛选口径和输出格式明确，包含查询、导出和文件检查，注明脱敏是否包含；取值依据：待填 |

### 6.5 历史数据迁移

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 数据处理 |
| 工作场景 | 使用已有工具或操作脚本完成历史数据迁移 |
| 工作内容及边界 | 确认迁移范围和映射规则、准备执行参数、执行迁移、核对结果；涉及试迁移或异常处理时注明；不含迁移工具的软件功能开发 |
| 交付内容 | 迁移操作记录、实际执行结果、源目标数据核对结果 |
| 交付方式 | 两者结合 |

| 评估标准（基线工时） | __人时／个迁移批次；适用条件：注明源目标范围、映射转换和核对要求，使用已有工具，包含参数准备、执行操作及结果核对；取值依据：待填；试迁移、异常处理或持续值守需说明是否包含及计量方式 |

### 6.6 业务数据差异核对

| 字段 | 示例填写 |
| --- | --- |
| 工作类别 | 数据核对 |
| 工作场景 | 跨系统或跨报表的数据差异核对 |
| 工作内容及边界 | 对齐核对口径、执行比较、识别差异、说明差异原因或待查事项；不含实际数据修正 |
| 交付内容 | 核对口径、差异情况和核对结论 |
| 交付方式 | 少量汇总核对可在任务描述中写明；涉及逐条差异清单时采用两者结合 |
| 交付要求 | 描述中写明核对对象、范围、口径、比较结果和结论；逐条核对时附差异清单，并保留查询或比较过程材料；无差异时记录核对范围及一致结论，无需编造差异清单 |
| 评估标准（基线工时） | __人时／套核对；适用条件：注明核对对象、指标及规则范围，包含比较、差异整理和结论；取值依据：待填；逐条人工核对或深入原因定位需另说明适用工时 |

| 评估标准（基线工时） | __人时／次发布；适用条件：注明环境、服务和验证范围，沿用既有发布流程，包含准备、部署操作及验证；取值依据：待填；回滚或持续值守需说明是否包含及计量方式 |

## 7. 常见填写问题

修改模糊条目时，优先补充交付内容、适用条件和边界。无需通过增加文件数量来让条目显得完整。

| 常见写法 | 存在的问题 | 建议修改 |
| --- | --- | --- |
| 工作场景：其他维护 | 无法识别具体工作 | 改为“配置调整及验证”“历史数据修正”等具体场景 |
| 交付内容：完成分析 | 没有说明留下什么结果 | 写明分析口径、过程、结果及结论 |
| 交付方式：交产出包 | 没有说明交付载体 | 选择描述、附件或两者结合，并列出各自内容 |
| 所有场景必须附截图、日志和报告 | 未考虑不同场景的产物 | 逐场景列出必要材料，简短结果可直接写在描述中 |
| 将完整结果表再抄到任务描述 | 重复填写且不便维护 | 结果表以附件交付，描述中写结论或附件索引 |
| 交付要求：必须成功、必须解决 | 未说明未完成时如何记录 | 写明完成判断；未完成时记录实际结果和遗留事项 |
| 评估标准：难度大，需要两天 | 缺少计量单位、适用条件及取值依据 | 改为“__人时／单位”，写清覆盖范围和工时依据；分档时明确条件 |
| 评估标准：待确认 | 未说明哪些内容无法确定 | 先填写计量单位和适用条件，明确基线数值或取值依据待确认 |
| 工作内容：备份、试跑、回滚、值守全部包含 | 把条件性活动列成固定范围 | 根据场景写“涉及……时包含……”，明确独立工作边界 |

提交前逐项确认：

- 每行描述一种工作场景，其他项目也能理解和使用。
- 工作内容包含明确边界，相邻场景没有重复覆盖同一工作。
- 交付内容写清过程、结论或结果，不只写工作动作。
- 交付方式说明哪些内容直接写在任务描述中，哪些需要附件。
- 附件要求区分必要材料、条件材料和可替代形式。
- 交付要求让执行人知道如何准备，让查看人知道如何检查。
- 评估标准（基线工时）写明计量单位、适用条件和取值依据；建议值或待确认项有明确标注。
- 基线工时覆盖约定工作及交付准备，人工投入与自动运行、等待时间区分，重复活动没有重复计入。
- 未达成共识的要求标注“待确认”，示例要求没有被直接当作既定制度。
